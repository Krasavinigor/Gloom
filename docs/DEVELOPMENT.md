# Локальная разработка

Обновлено: 16 октября 2026 года. Этапы 1–5 завершены: независимое демо, личный гардероб, место и погода, распознавание одежды и ручной подбор образов с заменами и готовыми фонами. Итоги проверок приведены ниже. Демо и ручной гардероб работают без OpenAI.

## Запуск

Нужны Node.js 24 (в `.nvmrc` закреплён `24.21.0`), pnpm `12.11.2` и работающий Docker Desktop. После `nvm use` проверь `pnpm --version`. Если pnpm ещё не установлен, используй [официальную инструкцию установки](https://pnpm.io/installation/); точная версия проекта закреплена в `packageManager`.

Из корня проекта:

```sh
pnpm install --frozen-lockfile
pnpm db:up
pnpm db:migrate
pnpm dev
```

Личный гардероб открывается на [127.0.0.1:3000/wardrobe](http://127.0.0.1:3000/wardrobe), место и погода — на [/outfits](http://127.0.0.1:3000/outfits), независимое демо — на [/demo](http://127.0.0.1:3000/demo). Сервер Next.js и порт БД доступны только на loopback.

Для текущего компьютера `.env.local` уже подготовлен: пароль локальной БД сгенерирован, файл исключён из Git. Существующий `.env` сохранён. На другом компьютере создай `.env.local` по `.env.example`, задай случайный `POSTGRES_PASSWORD` и соответствующий `DATABASE_URL`; стандартный порт — `55432`. Пароль внутри URL должен быть URL-encoded. PostgreSQL хранит данные в томе `wardrobe-weather_postgres_data`.

Демо запускается и без БД, и без ключа OpenAI: достаточно установки зависимостей и `pnpm dev`. Личный гардероб требует PostgreSQL и доступную приватную папку фотографий. `ENABLE_AI=false` в `.env.example` по умолчанию; загрузка, ручное описание и изменение вещей не обращаются к OpenAI. Для распознавания нужны `ENABLE_AI=true`, серверный `OPENAI_API_KEY` и отдельно запущенный worker. На текущем компьютере AI включён в `.env.local`, ключ остаётся в существующем `.env`. `.env.local` имеет приоритет над `.env`, поэтому не добавляй пустое переопределение ключа.

Фотографии хранятся в `.data/photos`, вне `public` и Git; путь задаётся через `FILE_STORAGE_ROOT`. Подготовка хранилища создаёт отдельную папку с правами `0700`, отклоняет небезопасные существующие папки и ссылки на публичные/родительские каталоги. Нормализованные JPEG-файлы имеют права `0600`, имя формируется из серверного UUID. Имя загруженного файла не используется как путь хранения.

## Личный гардероб

На странице `/wardrobe` загрузи одну фотографию одной вещи, заполни карточку и нажми сохранение. Черновик не входит в гардероб до сохранения. Фото черновика сохраняется на 24 часа и доступно после перезагрузки по адресу `/wardrobe?draft=<UUID>`. Ещё не сохранённые правки полей формы при перезагрузке теряются; после сохранения описание хранится в PostgreSQL.

Первоначальный список читается на сервере для SSR. Последующие чтения и изменения выполняются через TanStack Query; время актуальности клиентского кеша — 60 секунд. После изменения список обновляется. Редактирование и удаление передают версию карточки: если она уже изменилась, сервер отвечает `409`, а интерфейс предлагает обновить данные. Повторное сохранение того же черновика с теми же полями возвращает созданную вещь; повторное удаление не создаёт побочных эффектов.

### Фотографии и очистка

Принимаются JPEG, PNG и WebP размером до **10 МиБ**, до **40 Мп** и до **8192 пикселей** по стороне. Проверяется содержимое файла; анимация запрещена. Входящий поток ограничивается до разбора multipart: до 10 МиБ файла и 64 КиБ служебного оформления запроса. Обрабатываются не более двух загрузок одновременно.

Sharp поворачивает фотографию по ориентации, удаляет метаданные, включая EXIF/GPS, и создаёт две JPEG-копии: до 2048 пикселей для интерфейса и до 1536 для распознавания AI. Маленькие фотографии не увеличиваются; прозрачность заменяется белым фоном. Оригинал не сохраняется. На каждую копию установлен предел обработки 30 секунд; создание AI-копии не вызывает OpenAI.

Фото выдаётся только через `/api/assets/<UUID>` после проверки состояния в БД, без публичного пути и кеширования. Просроченный или отменённый черновик, удалённая вещь и фотография в состоянии `delete_pending` недоступны, даже если физический файл ещё существует. Если файл пропал отдельно от записи БД, API возвращает `photo_missing`, а карточка и описание вещи сохраняются.

Удаление сначала скрывает вещь и её фотографию, затем удаляет файлы. Если файловая операция не удалась, запись остаётся в состоянии ожидания очистки; её можно повторить из интерфейса. Для восстановления после перезапуска приложения:

```sh
pnpm storage:cleanup
```

Команда закрывает просроченные черновики, повторяет отложенное удаление и убирает файлы без записи в БД. Она рассматривает только собственные имена с UUID, включая временные файлы, старше одного часа и перед удалением повторно проверяет ссылки в БД. Свежие и используемые файлы сохраняются. Отсутствующий файл считается уже удалённым. Если часть очистки отложена, команда завершается с ненулевым кодом; повторный запуск безопасен.

Такая же очистка запускается при загрузке не чаще одного раза в минуту и при отмене черновика. Чтение гардероба ничего не удаляет. AI-worker дополнительно повторяет очистку раз в минуту. Если worker не запущен, после длительного простоя или сбоя используй команду очистки.

### API личного режима

| Метод и путь | Результат |
| --- | --- |
| `GET /api/garments` | Список сохранённых вещей и версия гардероба |
| `POST /api/garment-drafts` | Загрузка multipart-поля `photo`, создание черновика (`201`) |
| `GET /api/garment-drafts/:id` | Данные доступного черновика |
| `DELETE /api/garment-drafts/:id` | Отмена черновика и попытка очистки |
| `POST /api/garments` | Сохранение `draftId` и `fields` (`201`) |
| `PATCH /api/garments/:id` | Изменение `fields` с проверкой `version` |
| `DELETE /api/garments/:id` | Удаление с проверкой `version`; ответ содержит `cleanupPending` |
| `POST /api/garments/:id/cleanup` | Повтор физической очистки удалённой вещи |
| `GET /api/assets/:id` | Приватная нормализованная фотография JPEG |

JSON-ответы имеют вид `{ success: true, data }` или `{ success: false, error: { code, message } }`; выдача фотографии — бинарное исключение. Создание возвращает `Location`. Неверные поля дают `400`, запрещённый источник запроса — `403`, недоступная запись/фото — `404`, конфликт версии — `409`, превышение размера — `413`, неправильный тип запроса — `415`, неподходящее изображение — `422`, превышение лимита запросов — `429`. Ошибки не раскрывают пути, SQL или credentials.

Все маршруты приложения проверяют точный loopback-host (`127.0.0.1`, `localhost` или `[::1]`). Для API проверяется источник запроса, а для изменений обязателен `Origin`, совпадающий с адресом приложения. Лимиты общие для локального процесса: чтение — 600, изменения — 120, загрузки — 20 запросов в минуту. При `429` возвращается `Retry-After: 60`; перезапуск сбрасывает счётчики. Это локальный режим без авторизации, не схема размещения в интернете.

Чтение тела запроса ограничено 15 секундами. PostgreSQL использует серверный предел запроса 15 секунд, ожидание блокировки 5 секунд, клиентский предел 20 секунд и предел простоя транзакции 15 секунд. Недоступность БД не блокирует независимое демо.

### Резервная копия и восстановление

Останови приложение и другие процессы записи, включая `storage:cleanup`. При работающем PostgreSQL создай копию БД через `pg_dump` и скопируй всю приватную папку фотографий из того же состояния. Храни пару вместе и защищай копии: они содержат личные данные. Одной БД или одной папки недостаточно для восстановления гардероба с фотографиями.

Восстанавливай БД и файлы из одной пары при остановленном приложении. Сохрани приватные права папки `0700` и файлов `0600`, проверь `DATABASE_URL` и `FILE_STORAGE_ROOT`, затем запусти приложение и проверь карточки и фотографии. UI экспорта и автоматическое резервное копирование в первую версию не входят.

## Место и погода

На `/outfits` введи название города и выбери результат поиска. Open-Meteo Geocoding возвращает до восьми вариантов с регионом и страной. Сервер сохраняет выбранное место в PostgreSQL; повторное открытие страницы восстанавливает город и погодную сводку через SSR. Смена города не вызывает OpenAI и не запускает подбор образов: для подбора нужна отдельная кнопка.

При отсутствии сохранённого города браузер один раз пытается получить приблизительное место через `ipapi.co/json/`. IP-адрес не сохраняется и не передаётся нашему серверу: браузер отправляет только кандидата места, а сервер проверяет его поля, координаты и IANA timezone. Ручной поиск имеет приоритет; его начало отменяет клиентское определение. Сервер дополнительно проверяет `locationVersion` и отклоняет запоздалый IP-результат после изменения места (`409`). Сохранённое место не заменяется автоматически при следующем открытии страницы.

IP-провайдер может быть недоступен или ограничивать запросы. При живой проверке 15 октября он вернул HTTP `429` и заголовок CORS `Access-Control-Allow-Origin: *`; проверялись только статус и заголовок, тело с IP не читалось. Доступность автоматического определения не гарантируется. При ошибке интерфейс предлагает ручной выбор, который работает независимо от ipapi.co.

### Погодные данные и время

Сервер получает [Open-Meteo Forecast](https://open-meteo.com/en/docs) для сохранённых координат. Интерфейс отдельно показывает текущие условия и оценку на интервал от момента запроса до трёх часов спустя: температуру, ощущаемую температуру, ветер, порывы и осадки. Источник указан ссылкой Open-Meteo. Время получения `fetchedAt` подписано «Получено»; время текущих условий берётся из `current.time` провайдера и не подменяется временем загрузки.

Вычисления и хранение времени используют UTC. Для отображения применяется IANA timezone города через `Intl`, включая дату и смещение UTC: переходы через полночь и смена летнего времени не меняют трёхчасовую длительность. Температура, ощущаемая температура и скорость ветра оцениваются по почасовым точкам внутри интервала и линейной интерполяции на его границах. Это ориентировочная оценка, не дополнительные измерения провайдера; текущие условия показаны отдельно.

Осадки, вероятность и порывы относятся к часовым интервалам провайдера. Используются целиком все часовые интервалы, пересекающие выбранные три часа; сумма осадков не распределяется пропорционально минутам. Например, выход в 12:30 даёт интервал 12:30–15:30, а осадки и порывы могут покрывать 12:00–16:00. Этот более широкий период выводится отдельной подписью, чтобы сумма за четыре часовых интервала не выглядела точным прогнозом осадков за три часа.

Публичные кеши PostgreSQL отделены от личного состояния: Geocoding — 24 часа по нормализованному запросу и параметрам, Forecast — 15 минут по координатам и полному набору параметров запроса. Название города не используется вместо координат. Публичный кеш Next.js для персональных ответов не применяется; запросы к провайдерам и ответы API используют `no-store`.

При неверных единицах, пропущенных полях или неполном временном покрытии ответ провайдера не считается свежим. При ошибке остаются только проверенные старые данные для того же места с явной пометкой «Устаревшие данные»; если подходящих данных нет, отображается «Погода недоступна». Вымышленный прогноз и погода предыдущего города не подставляются. Клиент раз в минуту проверяет возраст уже показанных данных по локальным часам и отмечает устаревание; сетевого поллинга нет. Кнопка «Обновить погоду» перечитывает данные, используя серверный кеш до истечения TTL. Обновление погоды не запускает AI.

### API места и погоды

| Метод и путь | Результат |
| --- | --- |
| `GET /api/location` | Сохранённое место, источник `manual` / `ip` и `locationVersion` |
| `PUT /api/location` | Сохранение места с проверкой `expectedVersion` |
| `GET /api/places?query=...` | Проверенные результаты поиска города |
| `GET /api/weather?locationVersion=...` | Погодный snapshot выбранного места с периодом, `fetchedAt` и статусом `fresh` / `stale` / `unavailable` |

Ручное сохранение принимает `placeId` и исходный поисковый `query`, затем находит место в ещё действующем серверном кеше; координаты клиента для ручного выбора не принимаются. Истёкший результат поиска даёт `409 search_expired` и требует повторного поиска. Изменение места проверяет версию в транзакции; погодный запрос проверяет её до и после обращения к источнику. Старый запрос после смены города возвращает `409 location_changed`. Общие JSON-ответы, HTTP-guards, лимиты и ограниченное чтение тела из раздела гардероба сохранены.

Для отдельной живой проверки без OpenAI:

```sh
pnpm check:weather
```

Команда создаёт собственную случайную схему в локальном PostgreSQL, применяет миграции, проверяет поиск и свежий прогноз Москвы и Берлина, затем удаляет только свою схему. Она обращается к внешним погодным сервисам и проверяет доступность ipapi.co, не читая IP-ответ. 15 октября оба прогноза успешно получены с timezone `Europe/Moscow` и `Europe/Berlin`; ограничение IP-сервиса описано выше. Личные данные не меняются, платные AI-вызовы не выполняются. Миграции места и погодных кешей также применены к локальной схеме приложения с сохранением гардероба.

## Подбор образов, замены и фон

На `/outfits` выбери город, проверь погоду и нажми «Подобрать образы». Открытие страницы, смена города, обновление погоды и reload не запускают платный запрос. Для подбора нужны сохранённые вещи, свежая погода, `ENABLE_AI=true`, серверный ключ, доступный бюджет и отдельный worker. Недостаточный гардероб отличается от некорректного ответа AI.

Запуск фиксирует один snapshot: интервал от принятия действия до трёх часов спустя, место, UTC/IANA время, прогноз, поля вещей и версии гардероба/места. В OpenAI передаются описания и погодные условия, без фотографий. После проверки JSON-схемы сервер отдельно проверяет ID, роли, комплектность, слои, погоду и уникальность составов. Вещь с несколькими допустимыми слоями занимает одну роль; проверка комплектности распределяет разные вещи по обязательным ролям. Из 1–3 предложений публикуется допустимое подмножество. Неизвестная защита от дождя остаётся условной, температурные диапазоны — ориентировочными.

В БД хранится последний успешный результат с revision, snapshot и preset ID. Ошибка нового подбора сохраняет предыдущий. Перед допуском, dispatch, публикацией и заменой транзакция повторно проверяет версии и реальный погодный кеш под `FOR SHARE`. Погода сравнивается для сохранённого фиксированного интервала: новое время получения без изменения погодных фактов не делает результат устаревшим. Изменение гардероба, города, погодных условий, истечение трёхчасового периода или 15-минутной свежести отмечается в интерфейсе. Удалённая фотография не восстанавливается из старого результата. Reload восстанавливает результат или SSE-подписку на активную задачу.

«Заменить» предлагает проверенные альтернативы той же роли и повторно проверяет весь комплект. Замена бесплатна, сохраняет остальные вещи и увеличивает revision; конкурирующая правка со старой revision получает `409`. Замена, создающая одинаковые составы образов, отклоняется. Для устаревшего результата сначала нужен новый явный подбор.

Фон выбирается после успешного подбора из девяти готовых SVG: нейтральный, ясный день/вечер, небольшая/сплошная облачность, туман, дождь, снег и гроза. Учитываются коды всего периода; приоритет — гроза, снег/смешанные осадки, дождь, туман, облачность, ясная погода. Неизвестный код или preset использует нейтральный fallback. Фон не вызывает внешние сервисы, не резервирует бюджет и не задерживает образы; при ошибке изображения остаётся читаемый нейтральный фон.

## Распознавание одежды и AI-бюджет

После миграций запусти второй процесс из того же корня проекта:

```sh
NODE_USE_SYSTEM_CA=1 pnpm worker
```

Next.js и worker читают одинаковые env, PostgreSQL и приватную папку фотографий. После изменения env перезапусти оба процесса. На текущем Mac для доверия системным сертификатам запускай приложение также с `NODE_USE_SYSTEM_CA=1 pnpm dev` либо `NODE_USE_SYSTEM_CA=1 pnpm start` для готовой сборки. TLS-проверка остаётся включённой. Один worker обрабатывает распознавание и подбор, чередуя очереди, чтобы ошибки или постоянная загрузка одной очереди не блокировали другую. Если worker остановлен, задача остаётся в БД, но её deadline продолжает идти.

На `/wardrobe` загрузи фото и нажми «Распознать одежду». Перед кнопкой указано, что фото будет отправлено в OpenAI. Отправляется нормализованная AI-копия; загрузка сама по себе платный вызов не запускает. Результат появляется отдельным предложением: «Применить AI-описание к форме» заменяет поля формы, затем их можно исправить и сохранить. Приход результата не перезаписывает текущие правки или сохранённую вещь. Для нескольких основных вещей или отсутствия одежды показывается пояснение. Защита от дождя и ветра остаётся `unknown`, пока пользователь её не подтвердит; температура — приблизительная оценка.

Перезагрузка адреса черновика восстанавливает текущую операцию и результат. Статусы приходят через один SSE-feed с начальным снимком и `statusRevision`: PostgreSQL `LISTEN/NOTIFY` передаёт изменения, повторное подключение читает свежий снимок. Периодического GET-поллинга статусов нет; диагностический GET используется отдельно. Feed принимает до 20 UUID, закрывается после terminal-статусов и освобождает подписки при отключении. Разрыв канала PostgreSQL закрывает feed для восстановления связи.

Запуск использует `Idempotency-Key` с UUID; повтор той же попытки возвращает существующую операцию. Автоматических повторов платной мутации и запросов SDK нет. Deadline — 30 секунд с допуска операции, lease worker — 45 секунд. Проверка зависших операций выполняется раз в 5 секунд; получение очереди и очистка допускают внутренние таймеры. До отправки worker проверяет актуальность черновика в транзакции и фиксирует `dispatch_at`/`sent_unknown`. Отмена, успевшая до этой фиксации, предотвращает запрос. После фиксации запрос уже может выполняться: поздний результат не публикуется в отменённый, истёкший или сохранённый черновик. При неопределённом исходе резерв сохраняется и автоматического повтора нет.

### Учёт стоимости

Общий лимит — **$10 на календарный месяц UTC**, предупреждение — от **$8** с учётом резервов. Суммы хранятся целыми microUSD: $1 = 1 000 000. Допуск, операция и резерв фиксируются одной транзакцией с блокировкой месячной строки. При допуске сумма подтверждённых оценок, активных и неопределённых резервов и нового резерва не может превышать лимит. Неожиданно больший подтверждённый расход сохраняется полностью и ограничивает последующий допуск. Месяц определяется при допуске и сохраняется после полуночи/смены месяца.

Для распознавания модель — `gpt-6-luna`, Responses API, строгая JSON Schema, `store: false`, стандартный processing tier и максимум 1600 output tokens. Model ID, возможности и стандартные цены сверены 15 октября по [странице модели](https://developers.openai.com/api/docs/models/gpt-6-luna) и [официальным ценам](https://developers.openai.com/api/docs/pricing). Версия цен — `openai-standard-2026-10-15`, реализация — `src/server/recognition/pricing.ts`. До отправки резервируется **316 440 microUSD ($0.316440)**: весь допустимый контекст модели по максимальной применимой входной ставке, output cap и 20% запас. Это временная консервативная оценка, а не цена одного распознавания. Дополнительный вызов подсчёта токенов не выполняется: его биллинг не подтверждён.

После ответа резерв заменяется округлённой оценкой по provider usage и сохранённой версии цен. Если детали кеширования отсутствуют, все входные токены оцениваются по максимальной ставке cache write. До отправки сбой освобождает резерв; после возможной отправки без достоверного usage он переходит в `unknown`. Счёт провайдера может отличаться от оценки. Приложение ограничивает собственный допуск, не расходы других приложений или аккаунта OpenAI. Две исторические пробы этапа 0 (67 input и 20 output tokens, оценка $0.0000167) выполнены до ledger и не добавлялись задним числом: текущие счётчики начинаются с этапа 4. Неизвестный биллинг прежней пробы token-count также не представлен как подтверждённый расход. Новые проверки разработки проходят через общий ledger.

Для подбора используется та же модель и стандартные ставки, проверенные 16 октября; версия цен — `openai-standard-2026-10-16`, реализация — `src/server/outfits/pricing.ts`. Лимит ответа — **2400 output tokens**, резерв — **317 160 microUSD ($0.317160)** по полному контексту с запасом 20%. Это временный резерв, а не цена одного образа. Размер сериализованного входа ограничен 48 000 UTF-8 байт до допуска и перед dispatch. Фотографии в запрос подбора не отправляются.

### Сверка неопределённого расхода

```sh
pnpm ai:reconcile <operation-UUID> <provider-response.json>
```

Это локальная сверка без обращения к OpenAI, повторной генерации или публикации результата. Принимается terminal-операция распознавания или подбора с settlement `unknown` и JSON-файл до 64 КиБ: provider response ID (`id`), model, usage (`input_tokens`, `output_tokens`, при наличии `input_tokens_details.cached_tokens` и `cache_write_tokens`), при наличии `request_id` и `service_tier`. Хотя бы response ID или request ID должен совпадать с сохранённым у операции; модель и pricing revision проверяются. Если связать доказательство с операцией нельзя, резерв сохраняется. Не подставляй оценочные токены вместо подтверждённого provider usage; файл с данными провайдера храни вне Git.

## Решения при создании каркаса

- pnpm обновлён до **12.11.2** для обычного терминала на Intel Mac. Исходный 11.25.0 был проверен в среде Codex как JavaScript CLI; нативный pnpm из пользовательского терминала пытался переключиться на `@pnpm/exe@11.25.0` и падал с `ERR_PNPM_PNPM_ENGINE_NO_NATIVE_BINARY`. pnpm 12 имеет сборку macOS x64 согласно [списку поддерживаемых платформ](https://pnpm.io/installation/). Проверка версии остаётся включённой; `pmOnFail: ignore` не используется.
- Для lint-плагинов Next.js потребовались TypeScript **6.0.3** и ESLint **9.39.5**: первоначальные TS 7 / ESLint 10 не соответствовали их peer ranges. Проверка peers сохранена строгой. Точные зависимости закреплены в `pnpm-lock.yaml`; исторические результаты этапа 0 не заменяют итоговую установку и сборку.
- Knex и `pg` добавлены в `serverExternalPackages`: сервер использует установленные Node.js-пакеты напрямую, чтобы сборщик не включал необязательные драйверы других БД, на которые ссылается Knex.
- Next.js при запуске дописал свой блок в `AGENTS.md` с указанием локальной документации `node_modules/next/dist/docs`. Исходные правила ECC сохранены.
- `.env.local` раньше отслеживался Git с содержимым без реальных credentials. Файл исключён из индекса с сохранением рабочей копии; проверка локальной истории не обнаружила реальных секретов. Ключ OpenAI остаётся в неотслеживаемом `.env`.
- На этом Mac HyperKit оставлял PID-файл после остановки VM в Resource Saver. Настройка `UseResourceSaver` отключена с резервной копией `settings-store.json`; зависший PID-файл сохранён под другим именем. Контейнеры/образы/тома при исправлении не удалялись. После исправления PostgreSQL успешно запущен и пересоздан. Возврат Resource Saver может снова проявить проблему; Docker рекомендует современный [Apple Virtualization framework](https://docs.docker.com/desktop/features/vmm/) вместо устаревшего HyperKit.

## Локализация — этап 5a

Реализованы английский (`en`, по умолчанию) и русский (`ru`, по выбору в шапке). Настройка сохраняется в cookie `gloom-locale` для `/`; отсутствие или значение вне whitelist означает `en`. При SSR локаль читается на сервере, URL остаются прежними. Новых зависимостей и env-параметров нет.

- Типизированные словари находятся в `src/i18n/messages`, общий контекст и форматирование — в `src/i18n`. Интерфейс, ошибки, формы и подготовленные данные демо поддерживают оба языка.
- `POST /api/locale` сохраняет выбор без перезапуска AI и перемонтирования форм. Поля, файл/превью, результаты и ID задач сохраняются. Существующие пользовательские и AI-тексты автоматически не переводятся.
- Для геопоиска язык входит в ключ кеша; `searchLocale` позволяет выбрать результат, показанный до переключения. Погодные данные и сохранённое место от языка не зависят.
- Язык новых AI-ответов заморожен в `outputLocale` неизменяемого payload операции. Hash команды для идемпотентности не зависит от локали. Worker не читает текущую cookie; повтор с прежним ключом возвращает исходную задачу и её язык. Старые payload/результаты без поля используют `ru`.
