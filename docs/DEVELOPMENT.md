# Локальная разработка

Обновлено: 14 октября 2026 года. Этапы 1 и 2 завершены: независимое демо, личный гардероб и приватное хранение фотографий. Автоматические проверки и визуальная сверка desktop/mobile прошли.

## Запуск

Нужны Node.js 24 (в `.nvmrc` закреплён `24.21.0`), pnpm `12.11.2` и работающий Docker Desktop. После `nvm use` проверь `pnpm --version`. Если pnpm ещё не установлен, используй [официальную инструкцию установки](https://pnpm.io/installation/); точная версия проекта закреплена в `packageManager`.

Из корня проекта:

```sh
pnpm install --frozen-lockfile
pnpm db:up
pnpm db:migrate
pnpm dev
```

Личный гардероб открывается на [127.0.0.1:3000/wardrobe](http://127.0.0.1:3000/wardrobe), независимое демо — на [/demo](http://127.0.0.1:3000/demo). Сервер Next.js и порт БД доступны только на loopback.

Для текущего компьютера `.env.local` уже подготовлен: пароль локальной БД сгенерирован, файл исключён из Git. Существующий `.env` сохранён. На другом компьютере создай `.env.local` по `.env.example`, задай случайный `POSTGRES_PASSWORD` и соответствующий `DATABASE_URL`; стандартный порт — `55432`. Пароль внутри URL должен быть URL-encoded. PostgreSQL хранит данные в томе `wardrobe-weather_postgres_data`.

Демо запускается и без БД, и без ключа OpenAI: достаточно установки зависимостей и `pnpm dev`. Личный гардероб требует PostgreSQL и доступную приватную папку фотографий. `ENABLE_AI=false` по умолчанию; загрузка, ручное описание и изменение вещей не обращаются к OpenAI. AI-операции ещё не реализованы. `.env.local` имеет приоритет над `.env`, поэтому не добавляй пустое переопределение ключа, если он уже задан в `.env`.

Фотографии хранятся в `.data/photos`, вне `public` и Git; путь задаётся через `FILE_STORAGE_ROOT`. Подготовка хранилища создаёт отдельную папку с правами `0700`, отклоняет небезопасные существующие папки и ссылки на публичные/родительские каталоги. Нормализованные JPEG-файлы имеют права `0600`, имя формируется из серверного UUID. Имя загруженного файла не используется как путь хранения.

## Личный гардероб

На странице `/wardrobe` загрузи одну фотографию одной вещи, заполни карточку и нажми сохранение. Черновик не входит в гардероб до сохранения. Фото черновика сохраняется на 24 часа и доступно после перезагрузки по адресу `/wardrobe?draft=<UUID>`. Ещё не сохранённые правки полей формы при перезагрузке теряются; после сохранения описание хранится в PostgreSQL.

Первоначальный список читается на сервере для SSR. Последующие чтения и изменения выполняются через TanStack Query; время актуальности клиентского кеша — 60 секунд. После изменения список обновляется. Редактирование и удаление передают версию карточки: если она уже изменилась, сервер отвечает `409`, а интерфейс предлагает обновить данные. Повторное сохранение того же черновика с теми же полями возвращает созданную вещь; повторное удаление не создаёт побочных эффектов.

### Фотографии и очистка

Принимаются JPEG, PNG и WebP размером до **10 МиБ**, до **40 Мп** и до **8192 пикселей** по стороне. Проверяется содержимое файла; анимация запрещена. Входящий поток ограничивается до разбора multipart: до 10 МиБ файла и 64 КиБ служебного оформления запроса. Обрабатываются не более двух загрузок одновременно.

Sharp поворачивает фотографию по ориентации, удаляет метаданные, включая EXIF/GPS, и создаёт две JPEG-копии: до 2048 пикселей для интерфейса и до 1536 для будущего AI. Маленькие фотографии не увеличиваются; прозрачность заменяется белым фоном. Оригинал не сохраняется. На каждую копию установлен предел обработки 30 секунд; создание AI-копии не вызывает OpenAI.

Фото выдаётся только через `/api/assets/<UUID>` после проверки состояния в БД, без публичного пути и кеширования. Просроченный или отменённый черновик, удалённая вещь и фотография в состоянии `delete_pending` недоступны, даже если физический файл ещё существует. Если файл пропал отдельно от записи БД, API возвращает `photo_missing`, а карточка и описание вещи сохраняются.

Удаление сначала скрывает вещь и её фотографию, затем удаляет файлы. Если файловая операция не удалась, запись остаётся в состоянии ожидания очистки; её можно повторить из интерфейса. Для восстановления после перезапуска приложения:

```sh
pnpm storage:cleanup
```

Команда закрывает просроченные черновики, повторяет отложенное удаление и убирает файлы без записи в БД. Она рассматривает только собственные имена с UUID, включая временные файлы, старше одного часа и перед удалением повторно проверяет ссылки в БД. Свежие и используемые файлы сохраняются. Отсутствующий файл считается уже удалённым. Если часть очистки отложена, команда завершается с ненулевым кодом; повторный запуск безопасен.

Такая же очистка запускается при загрузке не чаще одного раза в минуту и при отмене черновика. Чтение гардероба ничего не удаляет. Постоянного фонового worker на этапе 2 нет; после длительного простоя или сбоя используй команду очистки.

### API личного режима

| Метод и путь | Результат |
| --- | --- |
| `GET /api/garments` | Список сохранённых вещей и версия гардероба |
| `POST /api/garment-drafts` | Загрузка multipart-поля `photo`, создание черновика (`201`) |
| `GET /api/garment-drafts/:id` | Данные доступного черновика |
| `DELETE /api/garment-drafts/:id` | Отмена черновика и попытка очистки |
| `POST /api/garments` | Сохранение `draftId` и `fields` (`201`) |
| `PATCH /api/garments/:id` | Изменение `fields` с проверкой `version` |
| `DELETE /api/garments/:id` | Удаление с проверкой `version`; ответ содержит `cleanupPending` |
| `POST /api/garments/:id/cleanup` | Повтор физической очистки удалённой вещи |
| `GET /api/assets/:id` | Приватная нормализованная фотография JPEG |

JSON-ответы имеют вид `{ success: true, data }` или `{ success: false, error: { code, message } }`; выдача фотографии — бинарное исключение. Создание возвращает `Location`. Неверные поля дают `400`, запрещённый источник запроса — `403`, недоступная запись/фото — `404`, конфликт версии — `409`, превышение размера — `413`, неправильный тип запроса — `415`, неподходящее изображение — `422`, превышение лимита запросов — `429`. Ошибки не раскрывают пути, SQL или credentials.

Все маршруты приложения проверяют точный loopback-host (`127.0.0.1`, `localhost` или `[::1]`). Для API проверяется источник запроса, а для изменений обязателен `Origin`, совпадающий с адресом приложения. Лимиты общие для локального процесса: чтение — 600, изменения — 120, загрузки — 20 запросов в минуту. При `429` возвращается `Retry-After: 60`; перезапуск сбрасывает счётчики. Это локальный режим без авторизации, не схема размещения в интернете.

Чтение тела запроса ограничено 15 секундами. PostgreSQL использует серверный предел запроса 15 секунд, ожидание блокировки 5 секунд, клиентский предел 20 секунд и предел простоя транзакции 15 секунд. Недоступность БД не блокирует независимое демо.

### Резервная копия и восстановление

Останови приложение и другие процессы записи, включая `storage:cleanup`. При работающем PostgreSQL создай копию БД через `pg_dump` и скопируй всю приватную папку фотографий из того же состояния. Храни пару вместе и защищай копии: они содержат личные данные. Одной БД или одной папки недостаточно для восстановления гардероба с фотографиями.

Восстанавливай БД и файлы из одной пары при остановленном приложении. Сохрани приватные права папки `0700` и файлов `0600`, проверь `DATABASE_URL` и `FILE_STORAGE_ROOT`, затем запусти приложение и проверь карточки и фотографии. UI экспорта и автоматическое резервное копирование в первую версию не входят.

## Проверки

### Форматирование UI

```sh
pnpm format
pnpm format:check
pnpm lint
```

`format` форматирует TSX-компоненты/страницы и CSS в `src`; `format:check` проверяет их без изменения файлов. Настройки — в `.prettierrc.json`: отступы два пробела, одинарные кавычки в JavaScript, ширина строки 100. `prettier-plugin-tailwindcss` сортирует классы в `className`, `cn`, `clsx` и `cva` с учётом темы Tailwind 4 из `src/app/globals.css`; параметры описаны в [документации плагина](https://github.com/tailwindlabs/prettier-plugin-tailwindcss). ESLint продолжает проверять код; `eslint-config-prettier` отключает конфликтующие правила оформления согласно [рекомендации Prettier](https://prettier.io/docs/integrating-with-linters). Секреты, артефакты сборки и workflow-файлы исключены через `.prettierignore`.

### Тесты и сборка

```sh
pnpm typecheck
pnpm lint
pnpm test
pnpm test:integration
pnpm test:coverage
pnpm exec playwright install chromium
pnpm test:e2e
pnpm test:persistence
pnpm build
```

Unit/component тесты не требуют БД. Для integration/coverage нужен запущенный локальный PostgreSQL: launcher загружает env, использует `INTEGRATION_DATABASE_URL` или локальный `DATABASE_URL`. Оба варианта ограничены loopback. Каждый тест создаёт случайную отдельную схему и удаляет только её; схема приложения и личные данные не очищаются.

`test:persistence` пересоздаёт **только контейнер PostgreSQL этого Compose-проекта**, сохраняя том. Тест проверяет адрес/порт/пользователя/БД, записывает контрольные данные в собственную случайную схему, читает их после пересоздания и удаляет тестовую схему. Выполняй отдельно от других тестов БД.

Браузерные тесты сначала собирают приложение. Launcher создаёт собственную случайную схему в локальном PostgreSQL и временную папку фотографий, применяет миграции и запускает отдельный production-сервер Next.js на `127.0.0.1:3100` с `ENABLE_AI=false` и без AI-ключа. После тестов удаляются только эта схема и временная папка; личные данные не очищаются. Прямой `playwright test` без подготовленной launcher схемы запрещён конфигурацией: используй `pnpm test:e2e`.

Проверяются демо, его изоляция, клавиатура и мобильная ширина, а также сценарий личного гардероба: загрузка → ручная карточка → сохранение → перезагрузка → редактирование → подтверждённое удаление. Внешние AI-вызовы для этих проверок не требуются.

## Решения при создании каркаса

- pnpm обновлён до **12.11.2** для обычного терминала на Intel Mac. Исходный 11.25.0 был проверен в среде Codex как JavaScript CLI; нативный pnpm из пользовательского терминала пытался переключиться на `@pnpm/exe@11.25.0` и падал с `ERR_PNPM_PNPM_ENGINE_NO_NATIVE_BINARY`. pnpm 12 имеет сборку macOS x64 согласно [списку поддерживаемых платформ](https://pnpm.io/installation/). Проверка версии остаётся включённой; `pmOnFail: ignore` не используется.
- Для lint-плагинов Next.js потребовались TypeScript **6.0.3** и ESLint **9.39.5**: первоначальные TS 7 / ESLint 10 не соответствовали их peer ranges. Проверка peers сохранена строгой. Точные зависимости закреплены в `pnpm-lock.yaml`; исторические результаты этапа 0 не заменяют итоговую установку и сборку.
- Knex и `pg` добавлены в `serverExternalPackages`: сервер использует установленные Node.js-пакеты напрямую, чтобы сборщик не включал необязательные драйверы других БД, на которые ссылается Knex.
- Next.js при запуске дописал свой блок в `AGENTS.md` с указанием локальной документации `node_modules/next/dist/docs`. Исходные правила ECC сохранены.
- `.env.local` раньше отслеживался Git с содержимым без реальных credentials. Файл исключён из индекса с сохранением рабочей копии; проверка локальной истории не обнаружила реальных секретов. Ключ OpenAI остаётся в неотслеживаемом `.env`.
- На этом Mac HyperKit оставлял PID-файл после остановки VM в Resource Saver. Настройка `UseResourceSaver` отключена с резервной копией `settings-store.json`; зависший PID-файл сохранён под другим именем. Контейнеры/образы/тома при исправлении не удалялись. После исправления PostgreSQL успешно запущен и пересоздан. Возврат Resource Saver может снова проявить проблему; Docker рекомендует современный [Apple Virtualization framework](https://docs.docker.com/desktop/features/vmm/) вместо устаревшего HyperKit.

Следующий функциональный этап — реальная погода и выбор места. AI-распознавание, AI-подбор, очередь, бюджет, полный каталог фонов и потоковый чат выполняются в последующих этапах принятого плана.
